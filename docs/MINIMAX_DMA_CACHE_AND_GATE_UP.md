# ТЗ: регистрации decode-кеша и приёмка объединённой передачи gate/up

Дата: 2026-10-22. Объект: strata-poly, DeepSeek, no-disk, одна NVIDIA GPU.
Рабочая база — коммит `7a2cf777` и последующие совместимые изменения, если они
появились. Перед изменениями проверить текущий diff и инструкции AGENTS.md.
Этот документ не является разрешением на самостоятельный повтор старых прогонов.

## Статус двух пунктов

| Пункт | Где работает | Текущий статус |
|---|---|---|
| A. Сохранение DMA-регистраций при пополнении экспертного кеша | Decode, обычный no-disk staging-кеш | Не реализовано: `follow_resident()` вызывает `prepare()`, который заменяет всё окно |
| B. Один H2D для gate/up | Batched MoE staging, в проверенных настройках — префилл | Уже реализовано в `7a2cf777`; проверить и закрыть, не писать повторно |

В коммите `7a2cf777` объединены три изменения под `--coalesce-expert-dma`:
подготовка ограниченного окна до attention, объединение диапазонов его регистрации
и соседних gate/up в одну передачу. Флаг включён в локальном JSON DeepSeek.
Обычный путь без флага сохраняет прежнюю политику.

`batched()` выбирает MoE staging при `n >= kStageRows`, сейчас `kStageRows=32`.
Это условие по числу строк, а не по имени фазы: для нестандартной speculative
пачки от 32 строк тот же путь теоретически возможен и при генерации. В проведённых
тестах decode использует меньшие окна и новый staging-путь там не выполнялся.

При пополнении обычного decode-кеша `[gate, up, down]` уже переносятся одним
`cudaMemcpyAsync` из исходной resident RAM в GPU-слот. Для этого пути задача
«объединить gate/up» отсутствует. Попадание в GPU-кеш не требует регистрации
источника или H2D: вычисление читает готовый слот VRAM.

## A. Сохранение регистраций источников decode-кеша

### Что исправить

Места: `Engine::follow_resident()` в `src/poly/engine.cpp`, `ResidentDma` в
`src/poly/resident_dma.hpp`, геометрия в `dma_ranges.hpp`.

Сейчас каждая изменившаяся пачка загрузок вызывает `prepare(sources)`. Тот делает
`clear()` после проверки на точное равенство: дожидается читателей, снимает все
свои регистрации и регистрирует новый набор. Пересечения с прежним набором
не сохраняются. Это не ошибка содержимого весов, а кандидат на лишние вызовы
и синхронизацию.

Нужна opt-in политика для обычного decode-кеша:

1. Сохранять уже зарегистрированные страницы, покрывающие нужные источники.
2. Добавлять только недостающие страницы, без перекрывающихся CUDA-регистраций.
3. Удалять старые целые регистрации при необходимости уложиться в прежний бюджет;
   не регистрировать всё RAM-хранилище и не увеличивать лимит ради результата.
4. Корректно выбирать жертв и обновлять возраст используемых регистраций.
   Не допускать снятия только что востребованного диапазона без необходимости.
5. Разделять время окончания DMA из RAM и время жизни GPU-копии. Наличие готового
   эксперта в GPU-кеше само по себе не требует держать его RAM-источник pinned.

Уже существует `retain()`, применяемый режимом обмена основных экспертов. Его
можно переиспользовать после проверки инвариантов, а не копировать алгоритм.
Нельзя считать механическую замену `prepare` на `retain` заранее доказанным
ускорением. Первое пополнение после префилла может встретить окно почти в 2.8 ГиБ;
нужна корректная обработка этой границы.

Для decode не применять полный охватывающий span из prefill: нужные эксперты
разбросаны по разным слоям огромной RAM-арены. Использовать реальные страницы
источников и сохранение пересечений в ограниченном окне.

### Инварианты

- Рейтинг, порог замены, число слотов и адаптация экспертного кеша не меняются.
- `[G,U,D]` продолжает копироваться одним H2D, без промежуточной host-копии.
- Не снимать регистрацию до окончания всех читающих её DMA, включая два потока
  и исключение между `begin()` и `end()`; сохранять безопасное разрушение объекта.
- Не смешивать CUDA-регистрации с одним лишь VirtualLock/mlock; pageable fallback
  не является допустимым незаметным результатом отказа регистрации.
- Лимит считается по реально зарегистрированным page-rounded диапазонам.
- Удаление регистрации в CUDA возможно только целиком: проверять частичные
  пересечения, разрывы и объединённые ранее диапазоны.
- Не затрагивать транзакции обмена основных RAM/VRAM-владельцев и их rollback.
- Переходы prefill -> decode -> prefill, park/restore и завершение процесса безопасны.
- При отказе регистрации состояние остаётся согласованным и очищаемым; не терять
  учёт внешней регистрации или уже работающего DMA.

Новую политику включать отдельно от существующего prefill-флага. Не менять
глобальное поведение по умолчанию без измеренного выигрыша. Не увеличивать
staging, rows, число потоков или запас памяти вместе с этим изменением.

### Измерения и приёмка

Сначала офлайн разобрать уже снятые счётчики. В предыдущем изменённом прогоне
полное `prepare` в decode A/B заняло 219.728/93.928 мс из 15.662/15.061 с.
Масштаб известной прямой цены — порядка 1.4%/0.6%, а не десятки процентов.
Нельзя обещать большой прирост ток/с из исчезновения этих вызовов.

Использовать существующую общую диагностику, добавив только отсутствующее:
сохранённые/добавленные/снятые страницы, причины eviction, calls и host API time,
полное время подготовки, ожидания, текущие/пиковые регистрации. Вложения таймеров
не складывать. Сопоставлять request/phase, CPU/GPU-экспертов, cache uploads/uses,
MTP accepted/offered и выходные ID. Не менять policy и не замораживать кеш ради
положительного результата.

Короткие синтетические проверки без модели: полностью покрытая пачка без новых
API; частичное пересечение; нехватка бюджета и выбор жертвы; два DMA-потока;
одна страница на стыке; окно после prefill; invalid geometry без потери старого
окна; частичный отказ регистрации; исключение до end; очистка и повторное применение.
Проверять байты данных, а не только число API-вызовов.

Модельный прогон, если разрешён пользователем: одна подготовленная серия со всеми
счётчиками одновременно. Длинный prefill, достаточно длинный decode с наполнением
и вытеснениями, следующий разговор и возврат, короткий prefill. Данные текущего
скрипта `tools/bench_poly_transfer_audit.py` и сохранённого тихого запуска использовать
как исходную точку. Не запускать отдельно модель на каждый новый счётчик.

Сравнивать расход самого процесса (working set/private commit, GPU used/asked/shared),
прямые аллокации и пик зарегистрированных страниц, а не общую свободную VRAM.
Retain может сократить API, но держать больше страниц между загрузками: цена драйвера
и памяти должна быть видна. Принимать по корректности и исчезнувшим операциям;
ускорением называть только измеренное изменение времени. Если стало хуже, оставить
политику выключенной и описать результат, а не скрывать его заморозкой кеша.

## B. Проверить и закрыть уже сделанный gate/up

Место: no-disk ветка `Engine::stage()` под `opt_.coalesce_expert_dma`.
Сейчас при `h.up == h.gate + L.gu_bytes` копируется `2*L.gu_bytes` одним H2D
в прежнюю смежную область staging. Down остаётся отдельным H2D. Для несмежных
источников сохранены две передачи gate/up. Padding и нулевой tail не менялись.

Подтверждено существующим длинным прогоном: 62646 -> 41764 основных H2D-вызова,
239896100864 байта в обоих вариантах. Host API time первого префилла:
0.385 -> 0.252 с. Это не снижение объёма весов и не отдельно измеренное ускорение
всего префилла: другие DMA-изменения включены тем же флагом.

Что осталось Минимаксу:

1. Проверить исходники и существующую проверку в `poly_resident_dma_probe`:
   original/merged staging совпадают побайтово, включая padding и tail,
   используются невыравненные размеры GU и два потока.
2. Офлайн подтвердить фактические gate/up/down байты и вызовы свежего тихого
   прогона по исходной числовой трассе. Короткий префилл не сравнивать как одинаковое
   число экспертов: адаптивная CPU share передала GPU больше работы.
3. Проверить fallback при несмежных источниках и допустимость двух полных GU
   внутри зарегистрированного диапазона, на границе окна и последнем эксперте.
   Если соответствующего случая нет в тесте, добавить короткую целевую проверку.
4. Закрыть пункт как уже реализованный после проверки. Исправлять код только при
   найденной ошибке; не добавлять вторую аналогичную оптимизацию decode-кеша.

Не нужен новый старый контроль или отдельный модельный прогон только для gate/up.
Если требуется доказать его независимый вклад в скорость, явно написать, что
имеющихся совмещённых замеров недостаточно. Новый A/B — только после отдельного
разрешения пользователя, не по собственной инициативе.

## Результат передачи

По A: отдельная opt-in правка, тесты безопасности, числовой баланс регистраций,
памяти и времени; по B: результат ревизии готовой реализации и закрытие либо
конкретная найденная ошибка. В отчёте разделять измеренное и предполагаемое,
данные/владельцев и скорость, API host time и GPU intervals/wall-time.

Не утверждать полное совпадение logits по одной успешной генерации. Для изменений
только управления страницами полезны полный logits-тест при фиксированных владельцах
и маршруте и обычная адаптивная проверка отдельно. Указать реально проверенные
backend'ы и режимы графов; отсутствие HIP/SYCL-среды не выдавать за успешную проверку.

Все завершённые результаты сохранять. Не останавливать чужие процессы и не
перезапускать уже идущий тест из-за изменения предпочтений. Сборки и длинные
запуски выполнять по разрешениям пользователя и AGENTS.md, заранее объявляя ожидание.
Планы/это ТЗ не коммитить: прямое указание пользователя. Реализацию коммитить
отдельно от отчётных материалов и не отправлять сообщения в чужие чаты без разрешения.
