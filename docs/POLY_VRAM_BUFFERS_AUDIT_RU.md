# ТЗ: проверить необходимость и размеры рабочих буферов strata-poly

## Цель

Для DeepSeek V4 Flash установить, какие выделения VRAM необходимы математике и текущей реализации,
какие завышены, какие можно объединить по времени жизни, а какие нужны только префиллу.
Нужны воспроизводимые измерения, проверка корректности и конкретный план экономии. Не удалять
буферы только потому, что они большие. Сначала инвентаризация и тесты; оптимизации — отдельными коммитами.

В соседней работе staging переиспользуется под адаптивный кэш экспертов при генерации. Не менять
этот механизм и не занимать его память постоянно под другие задачи. Не запускать одновременно
два больших GPU-теста или тест рядом с пользовательским сервером. Проверить текущий HEAD:
состояние кода может отличаться от приведённой исходной точки.

## Правила работы

- Репозиторий: `L:\AI_pictures_generate\PolyStrata`. Соблюдать AGENTS.md.
- Не читать личные логи, диалоги и промпты. Использовать собственные синтетические входы.
- Перед сборкой или долгим тестом объявить действие и ожидаемое время. Сборка требует разрешения пользователя.
- Каждое изменение коммитить отдельно. Не включать пользовательские изменения AGENTS.md и посторонние файлы.
- Не менять настройки по умолчанию, точность, CPU/GPU-размещение, число вычисляемых экспертов или размер
  батча ради красивой цифры экономии. Такие эксперименты допустимы только как явно названные варианты.
- Не выдавать Non Local/Shared Usage Windows за доказанное вытеснение CUDA-выделений из VRAM.

## 1. Инвентаризация выделений и времени жизни

Изучить `src/poly/engine.cpp` (`fbuf`, `alloc`, `shared_scratch`, `moe_rows`, `read`, `run`, `step`),
`src/poly/deepseek4.cpp` (`alloc_caches`, `assign_scratch`, `attention`, `squeeze`, `out_proj`),
`src/poly/mmq.cu`, `src/poly/resident_dma.hpp`, kernels и механизм записи CUDA graphs.

Добавить диагностический opt-in режим, который для каждого выделения или среза scratch сообщает:
имя, указатель/смещение, байты, dtype, форму, формулу, владельца, режимы использования и кратность
контексту/батчу/слоям/числу выбранных экспертов. Учесть выравнивание и защитные хвосты.
Сумма должна сходиться с текущими total и other в байтах; остаток объяснить.

Для каждого буфера перечислить производителей, потребителей, CUDA streams/events,
первую запись, последнее чтение и необходимость сохранения между токенами/слоями/запросами.
Разделить состояния внимания, активации, рабочие квантованные представления и метаданные.
Не считать разные имена доказательством необходимости разных физических участков.

## 2. Контролируемые эксперименты

Проверять по одной гипотезе. В отчёте различать: доказано по обращениям, проверено canary/санитайзером,
подтверждено сравнением результатов, подтверждено измерением скорости.

- `g_/u_/h_`: почему размер берётся по max dense/shared/2×expert FFN; какие реальные пределы
  требуются DeepSeek shared FFN, одиночной генерации, card_moe и батчевому MoE.
- `gu_/hx_/dx_`: нужно ли хранить все batch×top-k строки одновременно; проверить обработку группами
  экспертов/токенов и переиспользование после quantize/down/sum. Не менять порядок суммы незаметно.
- `q_/att_`, `oa_/ob_`, `t1_/qr_`, `ckv_/cscore_`, `iq_/iw_/score_`: построить интервалы жизни;
  проверить допустимые наложения и перезапись. Учесть чтение нескольких heads и CUDA graph replay.
- `r_`: разделить необходимость двух батчей для перекрытия копий при read и использование при decode.
- Кольца компрессоров: обосновать `rows + overlap`, накопление всех слоёв и сохранность состояния
  при переходах/откатах. Проверить уменьшенный внутренний chunk отдельно от внешнего батча.
- `wf_`: подтвердить 16 МиБ и реальные потребители; старая 2020 МиБ копия output head уже исключена.
- Квантованные входы и таблицы: выяснить, какие могут занимать одну память в разные моменты.
- Освобождение/переиспользование буферов только префилла при decode: измерить цену восстановления
  перед новым префиллом, влияние на размещение кэша, графы, задержку первого токена и пиковую память.

Для проверки границ применять canary и доступный Compute Sanitizer на коротких специально подобранных
входах. Не использовать санитайзерные скорости как обычный benchmark. Не делать alias, пока оба
потребителя могут работать на разных потоках; событие должно доказывать завершение последнего чтения.

## 3. Матрица тестов

Базовая серия: prompts 1k/10k/50k, decode не менее 512 токенов, по три измеряемых повтора после прогрева.
Граничные серии: батчи 1/8/31/32/33/256/1024/4096; context 16k/128k;
read chunk 4096/32768; последний неполный батч и граница компрессора ratio=4/128.
Для дорогих сочетаний достаточно коротких correctness-тестов; всю декартову матрицу длинно не прогонять.

Обязательные переходы: prefill→decode→новый prefill→decode, короткое продолжение с переиспользованием
контекста, отмена префилла/генерации и следующий запрос, session SAVE/RESTORE, speculative windows
и несколько последовательностей `step()`, если изменённый буфер участвует в этих путях.
Проверить `--rows-vram` и host rows для затронутых путей.

Correctness: одинаковые входные token IDs, seed, параметры и размещение экспертов. Фиксация кэша
допустима в отдельной серии сравнения численной корректности; для измерения производительности
адаптивный кэш включён, `STRATA_FREEZE_EXPERTS` отсутствует. Проверить logits на одинаковой принудительной
последовательности токенов: max/mean ошибки, NaN/Inf, argmax. Допуск обосновать контрольным шумом;
при неизменной арифметике требовать совпадение. Не сравнивать только произвольно разошедшиеся продолжения.

Производительность: load, TTFT, prefill tok/s, decode tok/s по окнам, CPU time, GPU hit rate,
число загрузок/вытеснений экспертов, H2D/D2H, текущие/пиковые VRAM и RAM, число/цена аллокаций.
Указать отдельно освобождённые requested bytes и фактическое изменение device free.
Не выдавать несколько выходных токенов за проверку прогрева кэша.

## 4. Сравнение с llama.cpp

Использовать тот же GGUF, устройство, контекст и физический микробатч (`n_ubatch`), а не только `n_batch`.
Указать commit llama.cpp, flash-attention, тип KV, offload и все параметры. Записать её compute buffers.
Показать соответствие MoE/attention тензоров и работу переиспользования в `ggml-alloc.c`.
Нельзя писать «в llama этого нет» только потому, что выделение называется compute buffer.
Если режимы вычислений отличаются, перечислить различия и не приписывать всю разницу аллокатору.
