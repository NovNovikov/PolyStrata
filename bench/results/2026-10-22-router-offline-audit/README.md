# Router: выводы из уже снятых данных, без нового запуска

2026-10-22. Новых запусков модели и сборок: **0**. Пересчитаны сохранённые
числовые данные тихой серии `2026-10-22-poly-dma-coalesced-idle`, сопоставлены
с исходниками её коммита `7a2cf777` и старым GPU phase probe от 2026-10-20.
Приватные разговоры, промпты и сессии не читались. Код движка не менялся.

## 1. Уже можно ограничить цену CPU-маршрутизации

В тихой серии 672 выданных токена, из них 668 межтокенных интервалов. Полный
decode_ms включает первые выборки/служебную работу; статистика после первого
output callback охватывает последующие вычисления модели.

| Последовательные интервалы вызывающего host-потока | За четыре запроса, с |
|---|---:|
| Полный decode wall-time | 37.643054 |
| Вызовы CPU-экспертов, включая ожидание workers | 22.092267 |
| Ожидание готовности router (`Stats::route_wait_ms`) | 11.998948 |
| Выходные ожидания logits/eval/window | 1.621497 |
| Полная подготовка DMA decode-кеша | 0.383619 |
| Остаток, включающий CPU-`route()` и прочую работу | **1.546723 (4.11%)** |

Это вычитание НЕ складывает GPU-время с CPU-временем. Проверен конкретный
single-GPU small-batch путь: таймер CPU начинается вокруг синхронного вызова
`cpu_experts()`; router-ready wait стоит до него; выходные stream waits стоят
после `run()`/в конце `window()`; `follow_resident()` готовит DMA на границе eval.
Соответствующие интервалы вызывающего потока не вложены друг в друга. GPU при этом
может работать параллельно CPU; время GPU повторно не добавляется.
CPU-таймер включает callback подачи GPU-работы/продолжения другой половины окна,
поэтому всю CPU-маршрутизацию и подачу GPU-команд нельзя считать новыми затратами
поверх него. Сверка касается этой конфигурации, не произвольного multi-GPU режима.

Из исходной audit-обёртки router wait получается 11.949898 с; разница с
Stats 11.998948 с — охват внешнего таймера и служебного учёта. Для вычитания
использован Stats, а не смесь этих двух величин.

Остаток — верхний бюджет для непосредственно неучтённой CPU-маршрутизации,
НЕ её отдельный замер. Там также sampler, учёт экспертов/кеша, код подачи,
планирование speculation, служебные расходы и диагностика. Он не ограничивает
эффект любой перестройки конвейера: изменение зависимостей может затронуть
учтённые интервалы. Но утверждение «CPU-маршрутизация занимает 11.95 с / 32%»
уже опровергается существующим кодом и числовым балансом.

## 2. Реальная GPU-работа до router уже профилировалась

Файл `2026-10-20-poly-cpu-bottleneck/phase-probe/engine/engine.stderr` содержит
101 scalar-position sample после исключения последнего prompt position, все
с 43 измеренными слоями. Пересчитаны исходные строки `GPU_PHASE`, а не только README.
Проба использует external event nodes, реально записываемые при CUDA graph replay.

| GPU-интервал по 43 слоям | Медиана, мс / scalar position |
|---|---:|
| HC + norm | 1.121 |
| Q/K/V | 2.707 |
| Compressor/indexer | 3.478 |
| Attention | 5.507 |
| Output projection | 3.749 |
| HC/FFN norm + router + host copy | 1.413 |
| Полный head, медиана сумм | **18.293** |

В том же старом прогоне host router-ready wait — 16.632 мс на output interval.
Ожидание GPU-события имеет сопоставимый масштаб с реальной GPU-работой, а не
представляет доказанный простой GPU ради CPU-`route()`.

У старой пробы контекст 22445/22446, 543 permanent experts, отдельный
диагностический exe; у свежей серии длинные входы 50000 и 567 permanent experts.
Эти времена нельзя вычитать из свежих 11.95 с или выдавать за фазовый баланс
нынешнего прогона. Они проверяют механизм и уже отвергают объяснение «всё время
ожидания router — лишний обмен/маршрутизация хоста».

Свежая общая диагностика хранит суммы по request/phase/layer и payload графов,
но `GpuSpan` внутри capture не даёт времени отдельных replay. Точных времён
GPU scores, D2H и последующего запуска для каждого свежего вызова там нет.
Придумывать их по числу байтов или по NVML utilization нельзя.

## 3. Излишний host-input payload уже посчитан

`router-host-x-unused-payload`: **43 случая, 704512 байт (0.672 МиБ)** за серию.
Исполненный D2H copy2 payload графов: около **492.6 МиБ**, capture templates
не включены. Отказ от заведомо ненужных входных данных — реальный небольшой
кандидат, а не объяснение многосекундного замедления.

При CPU-экспертах вход `xn_` всё равно нужен CPU: перенос GPU picks сокращает
scores примерно с 1 КиБ до 48 байт на строку, но не убирает 16 КиБ входа.
Следовательно, предложение «17 КБ -> 48 Б» неверно для смешанного пути.

## 4. CPU-вычисления подтверждены независимым измерением

В свежей тихой серии CPU-expert host spans дают **33.072 мс на output interval**.
Старый изолированный production CPU path для четырёх RAM-экспертов каждого из
43 слоёв даёт **33.145 мс** на 12 потоках: gate/up 20.587, down 12.171 мс.
Сырые данные: `2026-10-20-poly-cpu-bottleneck/isa-pair/stock.csv`.

Это сопоставление масштаба, а не тождество workloads: свежая серия имеет MTP,
адаптивный кеш и другой набор экспертов. Но большой CPU-expert таймер уже
подкреплён отдельной проверкой настоящих матричных вычислений.

## Вывод для следующего решения

Новый прогон не нужен, чтобы отвергнуть заявленные 32% стоимости CPU-маршрутизации,
закрыть большой эффект от удаления лишнего `xn_` payload и показать реальные
CPU/GPU-вычисления как основные статьи. GPU routing в mixed decode остаётся
кандидатом на улучшение расписания, но не доказанным способом вернуть треть времени.

Точный разрез свежей GPU-работы на scores/copy и чистую CPU-`route()` из этих
агрегатов не восстановить. Это ограничение имеющихся данных, а не основание
сразу перезапускать всю модель. Дополнительное измерение имеет смысл только
если выбранная конкретная правка действительно требует такого разреза.

`analyze.py` воспроизводит расчёт в `summary.json`, не запускает движок и
отказывается перезаписывать существующий summary. Материалы не коммитились.
