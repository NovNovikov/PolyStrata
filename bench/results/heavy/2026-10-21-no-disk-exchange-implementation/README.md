# No-disk: перестановка основных RAM/GPU-экспертов

**Исправление от 2026-10-21:** в измерителе обнаружена ошибка подготовки входа — шаблон
кодировался без `parse_special=True`. Сохранённый GLM-вход действительно содержит обычные BPE-части
вместо управляющих токенов. Приведённые ниже скорости сохранены как история эксперимента;
вывод о примерно +6% для обычного чата отозван. GPU-тесты переноса и арифметические тесты
планировщика от этой ошибки не зависят. Подробности и подготовленная проверка через реальный
серверный кодировщик: `../2026-10-21-deepseek-bat-prefill/README.md`.

Реализация: `afe10915`, защита незавершённой публикации владельцев: `975db9bf`.
Собран `build-poly-cuda12/strata-poly.exe`, которым пользуются текущие JSON. JSON и батники не менялись.
Все модельные процессы завершены. Отчёт и сырые результаты не коммитятся.

## Результат реализации

Флаг `--no-disk-expert-exchange` включает отдельный экспериментальный режим. Горячий RAM-эксперт
занимает основное GPU-место холодного, а холодный занимает освободившееся RAM-место горячего.
Gate/up/down переносятся без изменения квантизации. Единственная каноническая копия сохраняется;
временная копия холодного живёт внутри уже выделенного staging. Дополнительной арены весов нет.

Без флага остаётся прежний staging-кеш вторых копий. С флагом этот кеш выключен; staging служит
prefill и временным местом обмена. Вместимость основной арены сохраняется. Первый вариант меняет
экспертов только внутри слоя, поэтому не перераспределяет число GPU-мест между слоями.

Окно регистрации RAM ограничено, повторно использует диапазоны и вытесняет старые регистрации
после завершения DMA. При штатной ошибке переноса исходные данные восстанавливаются; если
согласованное состояние не подтверждено, последующие вычисления запрещаются.

Настройки и точная семантика мягкого бюджета: `docs/NO_DISK_EXCHANGE.md`.
По умолчанию один обмен за границу eval; `--no-disk-exchange-max N` позволяет 1–64.
Первый обмен допускается всегда, дальнейшие ограничивает мягкий бюджет; это не жёсткая гарантия
не превысить процент времени. Cooldown настраивается, по умолчанию 0; порог замены сохраняет
существующий гистерезис `recent(hot) >= 2*recent(cold)+2` с полураспадом 128 вычисленных строк.

## Скорость GLM

Тот же публичный технический промпт из предыдущего сравнения: **2050 token ID**, temperature=0,
seed=42. В каждом процессе три ответа по 512 токенов; в двух повторах восстановлено 2049 токенов.
Измерение напрямую через native `--serve`, без HTTP/UI. Отдельные копии публичного
`data/expert-profile-glm.txt`, отдельные session-каталоги, MTP включён, кеш не заморожен.

Общие параметры: контекст=200000, batch=1024, staging=2048 МиБ, chunk=8192, строки в RAM.
Для сравнения зафиксирован reserve=1024 МиБ; дополнительный загрузочный запас no-disk=512 МиБ.
Это параметры теста, а не изменение пользовательского конфига.

Tok/s = 511 интервалов / decode_ms между первым и последним из 512 токенов.
«Прогретая медиана» — медиана двух повторов, а не оценка с доверительным интервалом.

|---|---:|---:|---:|---:|---:|
| Старый no-disk staging-кеш, первый контроль | 20,67 | 20,81 | 18,43 | 19,62 | 26,49% |
| Новый обмен, лимит 1, финальная сборка | 19,15 | 18,80 | 21,09 | 19,95 | 31,01% |
| Новый обмен, лимит 2 | 18,72 | 20,54 | 21,52 | 21,03 | 32,49% |

| Новый обмен, лимит 8 | 20,26 | 21,08 | 20,60 | 20,84 | 33,38% |
| Старый no-disk staging-кеш, завершающий контроль | 23,43 | 20,57 | 21,08 | 20,83 | 27,21% |
| Обычный mmap | 17,35 | 27,92 | 29,89 | **28,90** | 43,69% |

Медиана четырёх прогретых контрольных ответов — **20,69 ток/с**. Лимит 4 выше неё на **5,98%**,
выше завершающего контроля на **5,29%**. Относительно только первого контроля получилось бы
+11,74%, но сам контроль к концу серии изменился на +6,13%. Поэтому результат описывается как
наблюдаемый выигрыш около 5–6% в этой серии, а не установленное универсальное ускорение на 12%.
Лимит 8 не улучшил результат. Консервативный лимит 1 преимущества над объединённым контролем
не показал. Настройки по умолчанию и JSON по этим данным не менялись.

Чистое сравнение первого контроля и лимитов 2/4/8 проведено одним бинарником
`939abfe8c148…` (сборка после `afe10915`). Финальные проверки моделей, лимит 1, mmap и завершающий
контроль — бинарником `49fb81a7ff12…` после `975db9bf`; добавлена защита ошибки публикации владельцев
и очистка регистрации при ошибке проверки. Полные SHA256 есть в `command.json` и сводках.

За три ответа лимиты 2/4/8 завершили **1363 / 2183 / 2465 обменов**. На третьем ответе с лимитом 4:
626 обменов, планирование 171 мс, регистрация 192 мс, переносы 596 мс, ожидание читателей 1,4 мс,
суммарное время транзакций 789 мс. Планирование показано отдельно; перекрывающиеся таймеры нельзя
складывать с CPU/GPU-временем как независимые части задержки.

### Ограничения сравнения

Выходные последовательности не идентичны. Относительно первого контроля no-disk ответы новых
режимов совпадают только первые 40–173 токена; mmap расходится с первого. Включённые CPU/GPU-пути,
MTP и автоматический выбор способа исполнения делают объём работы ответов различным. Это замер
естественных ответов на одинаковый вход, не идентичной последовательности вычислений.

Серия короткая, порядок в основном фиксированный; завершающий контроль добавлен для проверки
дрейфа. Пользовательские приложения не останавливались. Нет статистически установленного
ускорения на произвольных промптах. Обычный mmap остаётся заметно быстрее в этой серии; у него
больше GPU-мест и иная KV-политика. Точную цену каждого ограничения отдельно не измеряли.

В no-disk веса уже физически загружены при READY. В mmap первый prefill сопровождался
23,33 млн page faults процесса и 71,71 ГиБ системных дисковых чтений. Системные чтения не

prefill нельзя приписывать только изменению состава GPU-экспертов.

## Артефакты и что не проверено

`summary-final.json` — последняя сводка с замыкающим контролем. `summary.json` и первая
`verification.json` сохранены как промежуточные результаты; они не перезаписаны.
В каталогах запусков: точные команды и SHA256, READY, протокол, stderr, samples.jsonl, отдельные
запросы и results.json. Setup-файлы поздних запусков содержат исходные публичные token ID и хеш
исходного профиля. Все разговоры синтетические; личные журналы, промпты и профиль не читались.

Отдельно сохранены первоначальный пилот `glm-exchange` до исправления счётчика загрузок и ранний
`glm-smoke`, в котором дорогая проверка хешей повлияла на старый оценочный ограничитель бюджета.
Эта блокировка адаптации исправлена до основной серии. Эти пилоты не подставлены в основную таблицу.

Проверена сборка CUDA. HIP-инструментария на машине нет; HIP не собран и не проверен. SYCL-движок
эти исходники poly не использует. Не выполнено отдельное сравнение полных logits с численным
допуском при фиксированной раскладке, не снят равный поток принудительно заданных decode-токенов,
не проверен конкурентный multi-slot batch и обмен между слоями. Не заявляется ускорение DeepSeek:
там проведены проверки корректности и восстановления, не полноценное A/B скорости.
